## 전체 구조 요약

| 영역 | 스택 | 배포 |
|---|---|---|
| 프론트엔드 | Vite + React + TypeScript + React Router + Tailwind | Oracle VM (nginx로 정적 파일 서빙) 또는 Vercel |
| 백엔드(게임 서버) | Node.js + Socket.io | Oracle VM (PM2 상시 구동) |

**핵심 원칙**: 게임 상태(참가자, 보드, 호출 숫자, 턴, 승패)의 원본 소스는 항상 서버다. 프론트는 서버가 보내주는 상태를 그리기만 하고, 승패 판정이나 턴 관리 같은 로직은 절대 클라이언트에서 계산하지 않는다.

---

## 개발 순서 제안: 백엔드 먼저 뼈대 → 프론트 병행

소켓 이벤트 명세만 먼저 확정하면 프론트/백엔드를 거의 동시에 작업할 수 있다. 아래 순서를 권장한다.

1. **0단계**: 소켓 이벤트 명세 확정 (양쪽이 같은 계약을 보고 작업하기 위함)
2. **1단계**: 백엔드 - 방 생성/입장 로직만 먼저 (프론트가 붙어볼 수 있는 최소 기능)
3. **1단계**: 프론트 - 목업 데이터로 화면 레이아웃 먼저 (백엔드 기다리지 않고 UI부터)
4. **2단계**부터는 아래 표의 순서대로 서로 맞춰가며 통합

---

## 0단계: 공통 - 소켓 이벤트 명세 확정 (선행 작업)

프론트/백엔드 작업 시작 전에 아래를 문서로 먼저 고정한다. (`types/socket.ts`에 타입으로도 정의)

- 이벤트 이름 목록 (`create_room`, `join_room`, `set_board`, `call_number`, `number_called`, `game_over`, `send_chat` 등)
- 각 이벤트의 payload 타입
- 에러 케이스별 이벤트 (`room_full`, `room_not_found`, `invalid_board` 등)

> 이 문서가 프론트/백엔드 개발자(또는 AI 툴) 사이의 "계약서" 역할을 하므로, 변경이 필요하면 양쪽에 공지하고 같이 반영한다.

## 백엔드 개발 프로세스 (Node.js + Socket.io)

### 1단계 - 서버 뼈대 + 방 관리
- [ ] Express + Socket.io 서버 초기 세팅
- [ ] 인메모리 Room 저장소 구조 설계 (`Map<roomId, Room>`)
- [ ] `create_room`: room 생성, roomId 발급
- [ ] `join_room`: 닉네임 입력받아 참가자 추가, 정원(5명) 초과 시 `room_full` 응답
- [ ] `disconnect`: 접속 종료 시 방에서 참가자 제거/기권 처리
- [ ] **완료 기준**: Postman/socket.io 클라이언트 테스트 스크립트로 방 생성→입장→정원 초과 거부까지 확인 가능

### 2단계 - 빙고판 세팅 로직
- [ ] `set_board`: 유저가 배치한 1~25 보드 수신, 중복/누락 검증
- [ ] 검증 실패 시 명확한 에러 이벤트 반환
- [ ] 전원 준비 완료 시 `game_start` 브로드캐스트
- [ ] **완료 기준**: 여러 클라이언트로 동시 접속 후 전원 보드 제출 시 게임 시작 이벤트가 정상적으로 전체에게 감

### 3단계 - 턴제 게임 진행 로직
- [ ] 턴 순서 관리 (입장 순서 기준)
- [ ] 10초 타이머: 서버가 `setTimeout`으로 관리, 시간 초과 시 서버가 남은 숫자 중 랜덤 자동 호출
- [ ] `call_number`: 클라이언트가 보낸 숫자 유효성 검증(이미 호출된 숫자인지 등) 후 처리
- [ ] `number_called` 브로드캐스트 시 전원의 마킹 결과 포함해서 전송
- [ ] 라인 완성(가로5+세로5+대각선2=12줄) 체크 로직 → 3줄 완성 시 즉시 게임 종료 처리
- [ ] 동시 달성(공동 우승) 케이스 처리
- [ ] **완료 기준**: 자동 진행 스크립트(또는 여러 브라우저 탭)로 풀 게임 1회를 처음부터 끝까지(방생성→세팅→턴진행→우승자 결정) 오류 없이 완주

### 4단계 - 게임 종료 및 재시작
- [ ] `game_over`: 우승자 정보 + 전원 보드 공개 데이터 전송
- [ ] `restart_game`: 방 상태 초기화 후 세팅 단계로 복귀
- [ ] **완료 기준**: 종료 후 재시작 시 이전 라운드 데이터가 남지 않고 완전히 초기화됨

### 5단계 - 채팅
- [ ] `send_chat` / `chat_message`: 방 단위 브로드캐스트
- [ ] **완료 기준**: 대기실/게임 중 어느 시점에도 채팅 송수신 가능

### 6단계 - 배포
- [ ] Oracle VM에 Node 설치, PM2로 프로세스 등록
- [ ] nginx 리버스 프록시 + WebSocket Upgrade 헤더 설정
- [ ] SSL 인증서 적용 (Let's Encrypt)
- [ ] Security List(포트 80/443) 개방 확인

## 프론트엔드 개발 프로세스 (Vite + React + TS)

### 1단계 - 라우팅 + 화면 레이아웃 (백엔드 없이 목업으로 진행 가능)
- [ ] React Router 세팅: `/`(랜딩), `/room/:roomId`(방)
- [ ] 방 만들기 버튼 → 목업 roomId로 이동
- [ ] 좌(빙고판) / 우(채팅) 2분할 레이아웃 컴포넌트
- [ ] 닉네임 입력 화면
- [ ] **완료 기준**: 소켓 연결 없이도 화면 흐름(랜딩→닉네임 입력→방 화면)이 눈으로 확인 가능

### 2단계 - 소켓 연결 기반 마련
- [ ] `services/socket.ts`: 소켓 클라이언트 단일 인스턴스
- [ ] `useSocket` 훅: 연결 상태 관리
- [ ] `useRoom` 훅: 방 상태(참가자 목록 등) 구독
- [ ] **완료 기준**: 서버 1단계와 연동하여 실제 방 생성/입장이 동작, 정원 초과 시 에러 안내 노출

### 3단계 - 빙고판 세팅 UI
- [ ] 5x5 보드 컴포넌트, 1~25 숫자 배치 UI(클릭 방식 우선 구현, 이후 드래그 고려)
- [ ] 배치 완료 시 `set_board` emit
- [ ] 참가자별 준비 상태 표시
- [ ] **완료 기준**: 서버 2단계와 연동해 전원 준비 완료 시 게임 시작 화면으로 자동 전환

### 4단계 - 게임 진행 화면
- [ ] 내 턴 여부 표시 + 10초 카운트다운 UI
- [ ] 숫자 선택 UI (턴일 때만 활성화, 이미 호출된 숫자는 비활성화)
- [ ] `number_called` 수신 시 보드 마킹 애니메이션/표시
- [ ] 완성 라인 수 표시
- [ ] **완료 기준**: 서버 3단계와 연동해 여러 브라우저 탭으로 실제 턴 진행이 눈으로 확인 가능

### 5단계 - 게임 종료 화면
- [ ] 우승자 배너/모달
- [ ] 전체 참가자 보드 공개 뷰
- [ ] "다시 하기" 버튼
- [ ] **완료 기준**: 종료 후 재시작 시 세팅 화면으로 정상 복귀

### 6단계 - 채팅 UI
- [ ] 메시지 리스트 + 입력창
- [ ] 닉네임/타임스탬프 표시
- [ ] **완료 기준**: 대기실/게임 중 채팅 송수신 UI 정상 동작

### 7단계 - 배포
- [ ] `vite build`
- [ ] Oracle VM nginx로 정적 파일 서빙 (또는 Vercel 배포 시 소켓 서버 URL을 환경변수로 분리)

## 통합 테스트 체크리스트 (양쪽 다 준비된 후)

- [ ] 5명 동시 입장 후 6번째 유저 입장 거부되는지
- [ ] 보드 세팅 중 한 명이라도 미완료면 게임이 시작 안 되는지
- [ ] 턴 시간 초과 시 자동 호출이 정상 작동하는지
- [ ] 게임 중간에 한 명이 접속 종료해도 나머지 인원으로 게임이 계속되는지
- [ ] 3줄 완성 시점에 즉시 종료되고 전원 보드가 공개되는지
- [ ] 재시작 시 이전 라운드 상태가 남지 않는지

---

## 참고: 병렬 작업 시 프론트가 백엔드를 기다리지 않는 법

프론트 2~4단계는 백엔드가 아직 준비되지 않았어도, 소켓 이벤트 payload 타입만 미리 정의해두면 **mock 서버(같은 이벤트를 가짜로 응답하는 간단한 로컬 스크립트)** 를 만들어 붙여볼 수 있다. 0단계에서 정한 이벤트 명세를 그대로 mock에도 사용하면 나중에 실제 서버로 교체할 때 코드 변경이 거의 없다.
