# 0001. 실시간 통신을 Supabase Realtime으로 결정 (Node.js + Socket.io 서버 대체)

- 날짜: 2026-09-19
- 상태: 채택

## Context
초기 문서(`README.md`, `docs/content/index.md`, `기획/게임흐름.md`, `개발/개발프로세스.md`)는 Node.js + Express + Socket.io로 별도 게임 서버를 두고, 그 서버가 방/게임 상태의 원본 소스를 인메모리로 관리하는 구조를 전제로 작성되어 있었다.

반면 루트 `AGENTS.md`의 "프로젝트 설정" 섹션은 별도 게임 서버 없이 Supabase Realtime(Broadcast + Presence)을 사용하고, 각 클라이언트가 자신의 빙고판/마킹 상태를 로컬에서 직접 계산하며 서버는 이벤트 중계만 담당하는 구조를 전제로 이미 작성되어 있었다. 두 문서 세트가 서로 다른 아키텍처를 가정하고 있어, 신규 세션이 어느 쪽을 기준으로 구현해야 할지 알 수 없는 상태였다.

## Decision
Supabase Realtime 기준으로 통일한다.

- 별도 Node.js/Express/Socket.io 백엔드 서버를 두지 않는다.
- 방(room)마다 `bingo-room-{roomId}` Realtime 채널을 구독하고, Broadcast 이벤트(kebab-case)와 Presence로 참가자/게임 진행 상태를 동기화한다.
- 게임 상태의 원본 소스는 각 클라이언트이며, Supabase는 이벤트 중계 역할만 한다.
- 턴 타이머 관리, 시간 초과 시 자동 호출, 동시 우승 시 최종 승자 확정처럼 "대표 계산"이 필요한 로직은 **방장(호스트) 클라이언트**가 맡는다. 호스트는 Presence 입장 시각이 가장 이른 참가자이며, 호스트가 이탈하면 다음 순번이 자동으로 이어받는다.
- 서버 DB에 게임 데이터를 영구 저장하지 않는다(새로고침/전원 퇴장 시 초기화). 재접속 시에는 `request-state`/`state-sync` 이벤트로 다른 클라이언트로부터 상태를 재동기화한다.

## Consequences
- 별도 백엔드 서버 개발/배포/운영(Oracle VM PM2, WebSocket 리버스 프록시, 서버 스케일링 등)이 필요 없어져 인프라가 단순해진다.
- 반대로 턴 타이머, 승자 확정처럼 원래 서버가 중앙에서 강제하던 로직을 "호스트 클라이언트"라는 신뢰 기반 대표 모델로 옮겼다. 소규모(최대 5명) 지인 간 캐주얼 게임이라는 전제하에는 허용 가능한 트레이드오프지만, 호스트 클라이언트가 악의적이거나 버그가 있을 경우 게임 전체 진행에 영향을 줄 수 있다는 한계가 있다.
- 새로고침/재접속 시 상태 복구가 서버 재조회가 아니라 다른 클라이언트와의 재동기화(`request-state`)에 의존하게 되어, 전원이 동시에 새로고침하면 상태를 복구할 곳이 없다는 엣지 케이스가 생긴다.
- 이 결정에 맞춰 `README.md`, `docs/content/index.md`, `docs/content/기획/게임흐름.md`, `docs/content/개발/개발프로세스.md`, 루트 `AGENTS.md`의 "통신 규칙" 섹션을 함께 갱신했다(2026-09-19).
